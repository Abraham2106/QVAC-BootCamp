Designing Local-First Architectures

Módulo 4 — Drop-in Sovereignty · Baseline: QVAC SDK v0.18.x / v0.18.1 · Verifica las release notes antes de impartir.

Pregunta esencial

¿Debe todo correr local? No: la arquitectura correcta hace visible qué datos, capacidades y fallos pueden cruzar una frontera.

Esta clase convierte “local-first” en una decisión arquitectónica explícita. Partimos del cliente OpenAI-compatible de la Clase 9 y diseñamos políticas de privacidad, disponibilidad, coste y calidad.

No asumimos que “todo local” siempre es la respuesta: un modelo remoto puede ser necesario para una capacidad ausente, pero solo después de evaluar datos, consentimiento y riesgo.

Qué aprenderás

  1. Definir “local-first” como política verificable, no como eslogan.
  2. Dibujar fronteras de datos, ejecución y confianza.
  3. Clasificar solicitudes por sensibilidad y capacidad requerida.
  4. Escribir un Architecture Decision Record (ADR) defendible.
  5. Diseñar fallback local/remoto con consentimiento, timeout y auditoría.
  6. Separar degradación de disponibilidad de degradación de calidad.
  7. Medir latencia, coste, disponibilidad y exposición de datos.
  8. Probar que una política bloquea exfiltración accidental.

De “todo local” a una política

Local-first significa que la ruta local es la primera opción compatible con los requisitos. La política se ejecuta por solicitud:

request → classify(data, capability, consent)
        → local route (preferred)
        → if unavailable: safe fallback or refuse
        → record decision + outcome (without sensitive content)

Hay tres fronteras que no deben confundirse. Cada una tiene su pregunta y su control:

FronteraPreguntaEjemplo de control
Datos¿Qué bytes salen del dispositivo?Red bloqueada para PII
Ejecución¿Dónde se calculan tokens?QVAC local / endpoint compatible
Confianza¿Quién puede observar o cambiar el resultado?Allowlist, TLS, logs minimizados
Nota
“Usaremos IA local por privacidad” no es una decisión: no dice qué es privado, qué pasa si el modelo no está cargado, ni qué prueba lo demuestra.

Frontera de datos

Definición: Límite explícito de qué bytes pueden salir del dispositivo hacia cualquier endpoint.

Uso: Clasificar cada solicitud antes de enrutar. Salud, credenciales y secretos son alta sensibilidad: nunca salen.

function classify(request) {
  if (request.contains.some((item) => ['health', 'credential', 'secret'].includes(item))) return 'high'
  if (request.contains.includes('confidential')) return 'medium'
  return 'low'
}
Resultado
Cada solicitud obtiene una sensibilidad sin imprimir su contenido. Alta → ruta local o rechazo.
Nota
El log de clasificación registra la decisión y el motivo, nunca el prompt completo.

Frontera de ejecución

Definición: Límite de dónde se calculan los tokens: runtime QVAC local o endpoint remoto compatible.

Uso: Preferir local siempre que esté disponible. La Clase 9 aporta el mecanismo (cliente OpenAI-compatible); esta clase aporta la política.

// la decisión y el transporte van separados:
// 1. decide() — política pura, sin red (testeable offline)
// 2. adapter  — ejecuta la ruta elegida (Clase 9)
Resultado
Puedes probar la privacidad sin encender ningún servidor: la política es una función pura.

Frontera de confianza

Definición: Límite de quién puede observar o alterar el resultado: endpoints permitidos, TLS, minimización de logs.

Uso: Allowlist de endpoints remotos + consentimiento vigente + mensajes que indican dónde se ejecutó cada respuesta.

Resultado
El usuario siempre sabe si su solicitud fue local, remote-consented o refuse, y por qué.
Nota
Un endpoint no permitido se rechaza antes de serializar el prompt, no después de enviarlo.

ADR

Definición: Architecture Decision Record corto que deja auditable el razonamiento: contexto, decisión, alternativas, invariantes, consecuencias, evidencia, fecha y dueño.

Uso: Defender la frontera ante producto, seguridad y auditoría. Sin ADR, cada incidente reabre la misma discusión.

# ADR-001: asistente de campo local-first
## Contexto — técnicos sin conexión estable + mejora opcional remota
## Decisión — local por defecto; remoto solo medio/bajo con consentimiento
## Alternativas descartadas — todo-cloud / todo-local sin fallback
## Invariantes — I1..I5 (no exfiltración, consentimiento, transparencia…)
## Consecuencias — latencia local vs calidad remota, costo, UX de rechazo
## Evidencia — comandos, fecha, modelo, p50/p95, bloqueos
## Fecha y dueño
Resultado
Una decisión útil incluye clase de datos, capacidad, SLO, política ante fallo y cómo se verificará.

Matriz de enrutamiento

Definición: Tabla que clasifica antes de enrutar: cada combinación de sensibilidad y capacidad tiene ruta por defecto y fallback.

Uso: Convertir la política en casos testeables. Cada fila es un test automatizado.

SensibilidadCapacidadRuta por defectoFallback
alta (credenciales, salud)resumenlocalrechazar
mediaredacciónlocalremoto solo con consentimiento
bajamodelo grandelocalremoto permitido, registrado
cualquieracapacidad no instaladainstalación/localexplicar bloqueo
Resultado
Cinco casos del lab con rutas esperadas: local, remote-consented o refuse + razón + código de política.

Invariantes I1–I5

Definición: Propiedades que ninguna ejecución puede violar, se caiga lo que se caiga.

Uso: Escribirlas antes de probar; el Break It las ataca una por una.

IDInvarianteAtaque del lab
I1Alta sensibilidad nunca salePII + runtime caído → debe ser refuse
I2Remoto requiere consentimiento vigenteConsentimiento revocado → refuse
I3La respuesta indica dónde se ejecutóRuta sin etiqueta → fallo de transparencia
I4Ningún fallback bloquea indefinidamenteEndpoint lento → timeout finito
I5Decisión registrada sin contenido sensibleLog con prompt → fallo de minimización
Resultado
Cada invariante tiene al menos una prueba automatizada que la demuestra.

Fallback seguro

Definición: Ruta remota condicionada a cuatro checks: autorización explícita, endpoint permitido, timeout acotado y ausencia de datos prohibidos.

Uso: El fallback no es un catch que envía el prompt a cualquier endpoint. Si un check falla, se rechaza con alternativa accionable.

export function decide(input) {
  if (input.localReady) return { route: 'local', reason: 'preferred local route' }
  if (input.sensitivity === 'high') return { route: 'refuse', reason: 'high-sensitivity data is local-only' }
  if (!input.consent) return { route: 'refuse', reason: 'remote fallback requires consent' }
  if (!input.endpointAllowed) return { route: 'refuse', reason: 'endpoint is not allowlisted' }
  if (input.timedOut) return { route: 'refuse', reason: 'fallback timeout exceeded' }
  return { route: 'remote', reason: 'consented and allowlisted fallback' }
}
Resultado
Orden conservado: local → sensibilidad → consentimiento → allowlist → timeout. Ejemplo en examples/02-fallback-policy.ts.
Nota
El orden importa: comprobar consentimiento antes que sensibilidad podría registrar datos prohibidos en el camino.

Degradación

Definición: Pérdida explícita y etiquetada de disponibilidad o de calidad cuando la ruta ideal no existe.

Uso: Distinguir estados en lugar de un binario éxito/fallo: local-success, remote-consented, local-unavailable, remote-denied, quality-degraded.

Resultado
La disponibilidad no justifica romper I1–I2: sin ruta segura, la respuesta es un rechazo comprensible, no un envío silencioso.

Referencia QVAC

Clasificador de privacidad

Definición: Función que mapea una solicitud a sensibilidad alta/media/baja sin imprimir su contenido.

Uso: Primera etapa del pipeline. Alta → local-only; resto → local-first.

EntradaTipoDescripción
idstringIdentificador opaco para logs (sin PII)
purposestringPropósito declarado: resume, rewrite, translate…
containsstring[]Etiquetas de contenido: health, credential, confidential…
needsstringCapacidad requerida para la matriz
 
for (const request of requests) {
  const sensitivity = classify(request)
  const route = sensitivity === 'high' ? 'local-only' : 'local-first'
  console.log(`${request.id}: ${sensitivity} → ${route} (${request.needs})`)
}
Resultado
Seis solicitudes clasificadas y justificadas en el lab. Ejecutable: examples/01-privacy-classifier.ts.

Política de fallback

Definición: Función pura decide() que recibe sensibilidad, disponibilidad local, consentimiento, allowlist y timeout.

Uso: Simular timeout y alta sensibilidad sin red. La salida es ruta + razón, lista para auditar.

const cases = [
  { sensitivity: 'high', localReady: false, consent: true, endpointAllowed: true },
  { sensitivity: 'medium', localReady: false, consent: false, endpointAllowed: true },
  { sensitivity: 'low', localReady: false, consent: true, endpointAllowed: true },
  { sensitivity: 'low', localReady: false, consent: true, endpointAllowed: true, timedOut: true },
]
for (const input of cases) console.log(decide(input))
Resultado
Remoto solo cuando hay consentimiento y nunca para datos prohibidos. Ejecutable: examples/02-fallback-policy.ts.
Nota
Separar decisión y transporte permite probar la privacidad sin depender de que un servidor esté encendido.

Ejemplo completo

Starter del lab con el orden de invariantes ya marcado. Tu trabajo: ampliar casos y el ADR. En lab/starter/architecture-lab-starter.ts.

// TODO: conserva el orden: local → sensibilidad → consentimiento → allowlist
export function route(request) {
  if (request.localReady) return 'local'
  if (request.sensitivity === 'high') return 'refuse'
  if (!request.consent || !request.endpointAllowed) return 'refuse'
  return 'remote'
}

const sample = [
  { id: 'high-offline', sensitivity: 'high', localReady: false, consent: true, endpointAllowed: true },
  { id: 'medium-consented', sensitivity: 'medium', localReady: false, consent: true, endpointAllowed: true },
  { id: 'low-local', sensitivity: 'low', localReady: true, consent: false, endpointAllowed: false },
]
for (const request of sample) console.log(request.id, route(request))
Resultado
high-offline → refuse, medium-consented → remote, low-local → local. Tres rutas, tres motivos.

Antes de ejecutar

Escribe tus predicciones antes de tocar código:

  1. P1: el modelo local está descargado pero no cargado. ¿Qué ruta obtienes y qué mensaje ve el usuario?
  2. P2: una solicitud médica encuentra el runtime local caído. ¿Se envía al remoto consentido o se rechaza?
  3. P3: el usuario no dio consentimiento remoto y local no está listo. ¿Qué invariante se activaría si igual lo enviaras?
  4. P4: el endpoint remoto tarda más que el timeout. ¿Qué estado registra el sistema?
  5. P5: inyectas un endpoint no permitido con consentimiento vigente. ¿En qué punto se rechaza: antes o después de serializar el prompt?

Práctica guiada

Lab — ADR + Safe Fallback (75–90 min). Guía en lab/README.md. Trabaja con una app de la Clase 9 o con los ejemplos de esta carpeta.

  1. Predice P1–P4 por escrito antes de ejecutar.
  2. Clasifica al menos seis solicitudes en alta/media/baja; justifica sin imprimir contenido.
  3. Escribe ADR-001-local-first.md: contexto, decisión, alternativas, invariantes, consecuencias, métricas, fecha y dueño + diagrama de fronteras.
  4. Implementa el fallback: añade simulación de timeout + solicitud de alta sensibilidad. Esperado: remoto solo con consentimiento, nunca para prohibidos.
  5. Rompe cada rama: runtime caído, consentimiento revocado, endpoint no permitido, timeout. Registra ruta, motivo, datos expuestos (cero en alta) y mensaje al usuario.
  6. Mide y defiende en 3 minutos: qué proteges, qué sacrificas y qué evidencia cambiaría tu decisión. Tabla p50/p95, éxito local, fallos y bloqueos.

Resumen

  • Local-first es política verificable: local por defecto, remoto solo condicionado, rechazo cuando toca.
  • Tres fronteras distintas: datos (qué sale), ejecución (dónde se calcula), confianza (quién observa).
  • El ADR deja la decisión auditable: contexto, alternativas, invariantes, consecuencias y evidencia.
  • El fallback exige consentimiento + allowlist + timeout + ausencia de prohibidos, en ese orden.
  • Decisión y transporte van separados: la política es testeable sin red.
  • Sin respuesta a “qué dato jamás sale y qué permiso activa el fallback”, la arquitectura no está lista.

Fin del Módulo 4 — Drop-in Sovereignty.

Definition of Done

  • Las tres fronteras (datos, ejecución y confianza) aparecen en un diagrama.
  • La matriz de rutas y sus invariantes tienen pruebas automatizadas.
  • El fallback remoto exige consentimiento y allowlist.
  • La respuesta expone la ruta usada y el motivo de degradación.
  • El Exfiltration Test pasa con red bloqueada y endpoint malicioso.
  • El ADR incluye trade-offs de latencia, coste, disponibilidad y privacidad.

Checkpoint de defensa

  1. ¿Qué diferencia hay entre frontera de datos, ejecución y confianza?
  2. Presenta tu ADR y nombra dos alternativas descartadas.
  3. ¿Qué invariantes impiden exfiltración?
  4. Muestra cinco casos de fallback y sus rutas resultantes.
  5. Reporta latencia, éxito local, bloqueos y contexto de medición.
  6. ¿Qué sacrificio de producto aceptas para preservar privacidad?

Checkpoint completo en assessment/checkpoint.md. Aprueba con respuestas concretas, logs reproducibles y nivel ≥3 en la rúbrica.
