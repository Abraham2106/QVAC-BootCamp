Models, GGUF and the QVAC Lifecycle

Baseline técnico: QVAC SDK v0.18.x / v0.18.1 · verificado contra docs oficiales y npm el 2026-08-25.

Pregunta esencial

¿Qué estamos cargando realmente cuando "cargamos un modelo"?

Resultados de aprendizaje

  1. Explicar qué contiene un modelo: arquitectura, tensors, pesos, tokenizer, metadata y chat template.
  2. Explicar el papel de GGUF como formato de inferencia, distinguiéndolo de un checkpoint de entrenamiento.
  3. Razonar sobre cuantización: qué se gana en memoria/velocidad y qué se arriesga en calidad.
  4. Interpretar nombres de catálogo: familia, escala, INST/base, variante de cuantización.
  5. Gestionar el ciclo de vida: find → download → validate → load → infer → reuse → unload → close.
  6. Comparar variantes con mediciones propias y justificar una elección con la matriz de decisión.

Por qué importa esto

La Clase 1 trató el modelo como una caja negra: downloadAsset() trajo ~0.6 GB y loadModel() los puso en memoria. Funcionó — pero quedaron preguntas: ¿por qué 0.6 GB y no 6? ¿Qué diferencia hay entre Q4_0 y Q4_K_M? ¿Qué significa INST?

Estas preguntas no son académicas. Elegir el modelo equivocado produce una de dos fallas garantizadas: la aplicación que no carga (memoria insuficiente) o la que decepciona (calidad por debajo de la tarea). Y a diferencia de la nube, en local la elección de modelo ES la decisión de arquitectura.

Hoy abrimos la caja negra. Al cerrarla, un nombre como QWEN3_4B_INST_Q4_K_M será un contrato que puedes leer, evaluar contra tu hardware y defender.

GGUF: el formato del ecosistema GGML/llama.cpp

GGUF es un formato binario que empaqueta en UN solo archivo todo lo que el runtime necesita: tensors (con cuantizaciones posiblemente mixtas), tokenizer y metadata rica. El motor de texto de QVAC (qvac-fabric-llm.cpp) consume exactamente este formato.

La propiedad clave para local-first: un GGUF es autocontenido y portable — un archivo, validado por checksum, listo para correr sin dependencias adicionales.

Cuantización: la negociación central

Los pesos se entrenan en precisión alta (F32/BF16/F16). La cuantización los re-expresa en menos bits: Q8, Q6, Q5, Q4, o esquemas mixtos (como Q4_K_M).

menos bits por peso
   ↓
menos almacenamiento + menos memoria + típicamente más velocidad
   ↓
posible pérdida de calidad (tarea-dependiente)
PrecisiónBits/pesoTamaño aprox. por 1B parámetros
F3232~4.0 GB
F1616~2.0 GB
Q88~1.0 GB
Q44~0.5–0.6 GB

Órdenes de magnitud para razonar, no promesas. Siempre mide el archivo real.

Leer nombres de modelo

QWEN3   → familia (arquitectura + linaje)
4B      → escala: ~4 mil millones de parámetros
INST    → instruction-tuned (sin esto: "base", completador crudo)
Q4_K_M  → cuantización: 4 bits, K-quants, variante mixta M

El nombre te dice ANTES de descargar: cuánta memoria necesitarás, qué tarea espera, y qué tan agresiva fue la compresión.

La matriz de decisión

calidad  ×  ajuste a la tarea  ×  memoria  ×  almacenamiento
   ×  latencia  ×  contexto  ×  hardware  ×  modalidad

No existe "el mejor modelo": existe el mejor modelo PARA una tarea EN un hardware CON una restricción. La matriz se evalúa con evidencia.

Modelo mental

  • El GGUF es el contenedor de envío; el modelo cargado es la máquina desplegada. El archivo en disco no "hace" nada. loadModel() lo despliega en RAM/VRAM.
  • Un worker, muchos modelos. QVAC usa un worker compartido por aplicación. Los modelos cargados permanecen disponibles hasta que los descargas.

Inside QVAC

Tres fuentes de modelos (documentadas)

  1. Registro distribuido vía constantes del SDK. Las constantes son punteros al registro — el paquete npm NO trae pesos embebidos.
  2. URL HTTP directa, con fallbackSrc solo para constantes.
  3. Ruta local con modelType explícito — sin validación de checksum de catálogo: la integridad es responsabilidad de tu aplicación.

Under the Hood

  • Al cargar se reservan dos cosas: los pesos (≈ tamaño del archivo) y la reserva de contexto (ctx_size), que alimenta el KV-cache. Por eso ctx_size: 8192 en una máquina justa falla aunque los pesos "caben".
  • Por qué Q4 cabe donde F16 no: mismos pesos, 4× menos bits por peso.
  • El backend importa: Metal/Vulkan. Sin Vulkan en Windows no hay fallback CPU.
  • La calidad de Q4 es tarea-dependiente: chat general → degradación pequeña; razonamiento fino/código → puede notarse. Se mide con TU tarea.

Worked Example

Comparar dos modelos con el MISMO prompt determinista:

import {
  close, completion, loadModel,
  LLAMA_3_2_1B_INST_Q4_0, QWEN3_600M_INST_Q4, unloadModel,
} from "@qvac/sdk";

const PROMPT = "Enumera tres ventajas de la inferencia local.";
const GEN = { temp: 0, seed: 42, predict: 128 };

for (const modelSrc of [QWEN3_600M_INST_Q4, LLAMA_3_2_1B_INST_Q4_0]) {
  const t0 = performance.now();
  const modelId = await loadModel({ modelSrc, modelConfig: { ctx_size: 2048 } });
  const loadMs = performance.now() - t0;

  const sentAt = performance.now();
  let ttft = null;
  const run = completion({ modelId,
    history: [{ role: "user", content: PROMPT }], stream: true,
    generationParams: GEN });
  for await (const ev of run.events) {
    if (ev.type === "contentDelta" && ttft === null) ttft = performance.now() - sentAt;
  }
  const final = await run.final;
  console.log({ loadMs, ttft, tps: final.stats?.tokensPerSecond });
  await unloadModel({ modelId, clearStorage: false });
}
void close();

Misconcepciones comunes

1
"Más parámetros siempre es mejor." Un 7B mal ajustado pierde contra un 1B bien elegido; y en hardware modesto el 7B no carga. La matriz es multi-factor.
2
"Q4 destruye la calidad." La degradación existe, es tarea-dependiente y suele ser pequeña en chat general. Se compara a ciegas con TU caso de uso.
3
"El GGUF se ejecuta solo." Es datos + metadata: sin runtime, tokenizer y memoria no es nada.
4
"El SDK trae los modelos incluidos." Las constantes son punteros al registro; los pesos se descargan, validan y cachean aparte.

Checkpoint

  1. (Recall) ¿Qué significan INST y Q4_K_M en QWEN3_4B_INST_Q4_K_M?
  2. (Explicación) ¿Por qué checkpoint y GGUF no son lo mismo? Dos diferencias.
  3. (Explicación) "Bajé a Q4 y ahora es 4× más inteligente porque es más rápido": dos errores en esa frase.
  4. (Aplicación) 6 GB disponibles, chat general offline: ¿escala y cuantización primero?
  5. (Aplicación) 7B Q4 (~4 GB) con 3 GB disponibles: ¿en qué fase falla y qué mensaje esperas?
  6. (Diagnóstico) modelRegistryList() falla por red pero la app carga por constante: explica el flujo.
  7. (Diagnóstico) GGUF por ruta local produce tokens basura: ¿qué pieza sospechas y por qué la validación de catálogo no ayudó?
  8. (Evaluación) TU máquina + "resumir documentos offline": matriz (≥5 factores) + riesgo + detección, en 5 líneas.

Takeaway

"Cargar un modelo" = desplegar a memoria un GGUF validado: pesos cuantizados + tokenizer + metadata, elegidos con la matriz de decisión y confirmados con mediciones. El nombre del modelo es un contrato; tu hardware es la contraparte. Lee ambos antes de prometer nada.
