QVAC · Módulo 4 · Clase 10

Designing
local-first architectures

La privacidad se diseña como política verificable, no como eslogan.

Pregunta esencial

¿Debe todo correr local?

No: la ruta correcta hace visible qué datos, capacidades y fallos pueden cruzar una frontera.

Política
request → classify(data, capability, consent) → local route (preferred) → safe fallback or refuse → record decision
Tres fronteras

Datos

¿Qué bytes salen?

Ejecución

¿Dónde calculan tokens?

Confianza

¿Quién observa o cambia el resultado?

Routing matrix
alta + sensible → local / rechazar media → local / remoto con consentimiento baja → local / remoto registrado capacidad ausente → explicar bloqueo
Fallback seguro

Un catch no es una política.

Requiere autorización, endpoint permitido, timeout acotado y ausencia de datos prohibidos.

Invariantes
  • I1: sensibilidad alta nunca sale.
  • I2: remoto requiere consentimiento vigente.
  • I3: la respuesta declara dónde se ejecutó.
  • I4: ningún fallback bloquea indefinidamente.
  • I5: registra decisión sin contenido sensible.
ADR
contexto → decisión → alternativas → invariantes → consecuencias → evidencia → dueño/fecha

“Usaremos IA local por privacidad” no es todavía una decisión auditable.

Degradación

Disponibilidad no es calidad.

Distingue local-success, remote-consented, local-unavailable, remote-denied y quality-degraded.

Break it

Bloquea red con PII y fuerza el fallback.

Predice qué debe ocurrir: nunca exfiltrar, explicar el bloqueo y registrar el intento.

Measure it

TTFT · latencia total · éxito · % rutas locales · timeouts · coste · intentos remotos bloqueados, siempre por clase de solicitud.

Definition of done
  • ☐ Fronteras de datos/ejecución/confianza dibujadas
  • ☐ Matriz y ADR reproducibles
  • ☐ Invariantes probadas con red bloqueada
  • ☐ Auditoría sin guardar contenido sensible
Takeaway

Local-first es una decisión observable.

Puente: conecta la arquitectura a la malla P2P y al capstone final.
