Local Inference FundamentalsConcepto03 / 24

Tokens ≠ palabras

  • Un LLM no consume "palabras" — el tokenizer convierte texto en tokens (unidades sub-palabra del vocabulario)
  • "Hola" puede ser 1 token; un término técnico compuesto puede ser 3; puntuación y espacios también cuentan
  • El costo de contexto escala con tokens procesados, no con "número de frases"
Regla práctica
No adivines conteos exactos sin medir con el tokenizer del modelo concreto. Si no tienes API de conteo verificada, usa proxies (caracteres, mensajes) y etiquétalos honestamente.

Generación autoregresiva

history / prompt
      ↓
tokenización
      ↓
evaluación del prompt (prefill)
      ↓
distribución del siguiente token
      ↓
sampling / selección
      ↓
append al contexto
      ↓
repetir hasta condición de parada

Cada token nuevo depende de todo lo anterior — incluidos los que el modelo acaba de generar. Por eso el streaming tiene sentido: puedes observar el bucle mientras ocurre.

Modelo mental — cadena causal

history → tokenization → model state (attention)
      ↓
next-token distribution → sampling → token
      ↓
streamed event (contentDelta) → repeat until stop
Pregunta de diseño
Cuando cambies un parámetro, pregúntate: ¿en qué eslabón de esta cadena actúa? temp → sampling · history larga → prefill · predict → stop condition.

Watch the stream — eventos clave

EventoRol pedagógico
contentDeltaFragmento de texto visible; primer evento útil para TTFT
completionStatsStats del runtime (p. ej. tok/s) durante o al final
completionDoneSeñal de cierre del stream; puede incluir stopReason

Streaming expone progreso al cliente — no acelera intrínsecamente el motor. tok/s del runtime puede ser idéntico con o sin streaming UX.

Local Inference Fundamentals§2 Superficie QVAC09 / 24

stopReason — por qué paró

ValorSignificado típico
"eos"Fin natural (end-of-sequence)
"length"Alcanzó límite de tokens nuevos (predict)
"stopSequence"Encontró secuencia de parada configurada
"cancelled" / "error"Cancelación explícita vs fallo mid-stream
Diagnóstico
stopReason: "length" no es "el modelo falló" — es el runtime obedeciendo un límite que tú configuraste. Evidencia: final.stopReason, contenido parcial, stats.

Sampling — reglas de selección

modelo predice candidatos al next token
        ↓
sampling elige uno → distintos settings → distinto comportamiento
generationParamsRol

temp altera selección, no el conocimiento en los pesos. Usa temp, no temperature.

Local Inference Fundamentals§3 Knobs y fases12 / 24

Presión de contexto

system / template (interno)
+ conversation history
+ retrieved context (RAG — Clase 6)
+ current user message
+ generation budget (predict)
= ventana finita
  • history no es decoración — es input de inferencia
  • History más larga → más trabajo de prefill antes del primer token → TTFT puede subir
  • "Si cabe en contexto, es gratis" es falso — más contexto = más procesamiento

TTFT · tok/s · latencia total

MétricaQué mideDónde
TTFTEspera hasta primer contentDeltaResponsividad percibida al inicio
tok/sThroughput de decode sostenidofinal.stats.tokensPerSecond
Latencia totalWall-clock request → finalTTFT + decode + overhead
Regla de oro
TTFT ≠ total latency ≠ tokens/sec. Dos configs con el mismo tok/s pueden sentirse muy distintas si difieren en TTFT o en cuántos tokens producen.
Local Inference Fundamentals§3 Knobs y fases14 / 24

KV cache y profiler

  • KV cache: reutiliza attention state (keys/values) de prefijos compatibles en follow-ups
  • kvCache: true — auto-cache SDK · "mi-sesion" — caller-managed
  • NO es memoria semántica, RAG ni garantía de speedup en prompts diminutos
  • Profiler: timing agregado por operación — profiler.enable() → exportSummary()
Tres capas de evidencia — no las mezcles
completionStats / final.stats → esa generación · Profiler → timing RPC/handler · Resource gauges → señales de backend (opt-in).

# Predict

Predict Before We Run — por escrito, antes de ejecutar. Comprometerse con un modelo mental es lo que convierte la observación en aprendizaje.

  1. Mismo prompt, seed: 42, temp: 0 vs temp: 1.0 — ¿salida idéntica?
  2. History corta vs larga — ¿qué métrica cambia primero: TTFT o tok/s?
  3. predict: 8 con prompt que pide respuesta larga — ¿qué stopReason esperas?
  4. Follow-up con kvCache: true vs sin cache — ¿dónde debería verse la diferencia?

Misconcepciones + Your Turn

Top 3

Challenge — Design a Responsive Local Generation Configuration

Local Inference Fundamentals§5 Cierre22 / 24

Checkpoint — demuéstralo

  1. ¿Por qué TTFT ≠ tok/s?
  2. ¿Por qué streaming puede sentir la app más rápida sin cambiar tok/s?
  3. ¿Cuándo ayuda KV cache en un follow-up?
  4. stopReason: "length" — ¿falló necesariamente?
  5. Mismo tok/s, TTFT muy distinto — dos causas plausibles
  6. Diseña experimento controlado: ¿contexto afecta responsividad?
Takeaway
La inferencia es un proceso con fases observables, no una llamada API opaca. Separa prompt latency de decode throughput, lee el event stream, y diseña un experimento antes de afirmar rendimiento.
