Tres ciclos de vida
Offline ChatArquitectura04 / 22

Tres relojes — no los mezcles

MODELO     find → load → reuse → unload → close
             (activo pesado · una carga)

REQUEST    completion → events → final / cancel
             (un turno · requestId propio)

CONVERSACIÓN  load history → user → generate → commit → persist
             (sobrevive requests · estado producto)

Generar es el eslabón donde los tres se encuentran — pero cada uno tiene reglas distintas.

Offline Chat§1 Ciclos06 / 22

El modelo no recuerda solo

  • Multi-turn = pasas history[] en cada call
  • Sin historial explícito → amnesia entre turnos
  • Historial = estado de producto, no memoria mágica
Anti-patrón en rojo
Confiar en que "el modelo ya sabe" lo del turno anterior. Eso es bug de arquitectura, no feature.

Stream vs commit
Offline ChatCommit08 / 22

Dos capas de verdad

events / contentDelta
        ↓
BUFFER PROVISIONAL  ← pantalla · crece en vivo
        ↓
   await final
        ↓
TURNO COMPROMETIDO  ← history[] · JSON · restart

Renderizar ≠ persistir. La UX ve el buffer; la conversación solo avanza tras commit.

Offline Chat§2 Commit10 / 22

Cancelar no es fallar

  • cancel({ requestId }) — acción de producto
  • Usuario pulsa stop → normal, no excepción genérica
  • length ≠ cancel · error ≠ cancel
Pregunta de aula
Cancelaste tras 40 caracteres streamados. ¿Van al JSON? Tú decides — pero debe ser consistente y documentado.

Definition of Done — preview
